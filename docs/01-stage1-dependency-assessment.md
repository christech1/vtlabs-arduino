## 2. Verified Arduino platform mechanisms

### 2.1 Core reference (the mechanism VTLabs will use)

A board in a third-party platform may use another vendor's core with `VENDOR_ID:CORE_ID`:

```
vtlabs_iot_esp32.build.core=esp32:esp32
```

Verified behaviour from the spec:

- The referenced core platform's `platform.txt` is inherited. VTLabs needs a `platform.txt` only for overrides.
- The referenced platform's bundled libraries (`WiFi`, `Wire`, `SPI`, …) are available; VTLabs libraries take priority on name clash.
- The referenced platform's programmers are available.
- The board's own `build.variant` resolves inside the **VTLabs** platform's `variants/` folder, so the VTLabs pin map lives in VTLabs's repo.
- Architecture is implied: VTLabs's architecture folder **must be `esp32`** for `esp32:esp32` to resolve.

### 2.2 Tool references

`upload.tool=VENDOR_ID:TOOL_ID` is supported. Not needed if the core reference is used, because the core's `platform.txt` (and its `esptool_py` recipe) is inherited.

### 2.3 Package index — dependency limitation (important)

A platform entry can declare `toolsDependencies`, `discoveryDependencies`, `monitorDependencies` and (since Arduino CLI 1.5.0 / IDE 2.4.0) `libraryDependencies`.

**There is no field for depending on another platform.** Installing "VTLabs IoT Training Kit" through Boards Manager will **not** install `esp32:esp32` automatically. Consequences:

- Students must install the Espressif "esp32" platform first (or the install guide must make that step explicit).
- The VTLabs platform cannot technically pin the core version. The supported core version must be documented and checked at build time (see §4.3).

Other verified index facts: 3rd-party `category` must be `Contributed`; checksums use `ALGORITHM:HEX` (SHA-256 recommended); index file name must match `package_<NAME>_index.json`; release archive must contain exactly one root folder; `.zip`, `.tar.bz2`, `.tar.gz` are the most compatible formats.

## 3. Verified Espressif core 3.3.12 facts

### 3.1 Generic "ESP32 Dev Module" defaults (`boards.txt`, board id `esp32`)

| Property | Value |
|---|---|
| `build.mcu` / `build.target` | `esp32` |
| `build.tarch` | `xtensa` |
| `build.f_cpu` | `240000000L` |
| `build.flash_size` | `4MB` |
| `build.flash_mode` / `build.boot` | `dio` / `dio` |
| `build.flash_freq` | `40m` |
| `build.partitions` | `default` |
| `build.bootloader_addr` | `0x1000` |
| `upload.maximum_size` | `1310720` |
| `upload.maximum_data_size` | `327680` |
| `upload.tool` / network | `esptool_py` / `esp_ota` |
| `serial.disableDTR` / `disableRTS` | `true` / `true` |

Menus defined: `CPUFreq, DebugLevel, EraseFlash, EventsCore, FlashFreq, FlashMode, FlashSize, JTAGAdapter, LoopCore, PSRAM, PartitionScheme, UploadSpeed, ZigbeeMode`.

These are only defaults for a generic module; they must be confirmed against the actual VTLabs module (§5).

### 3.2 Generic variant pin map (`variants/esp32/pins_arduino.h`)

TX=1, RX=3, SDA=21, SCL=22, SS=5, MOSI=23, MISO=19, SCK=18, DAC1=25, DAC2=26, plus A0…A19 and T0…T9 touch aliases. VTLabs will define its own variant; these values are only the starting reference.

### 3.3 Variant-local partition table is supported

`platform.txt` copies `{build.variant.path}/partitions.csv` (property `build.custom_partitions=partitions`) over the selected scheme. A VTLabs variant can therefore ship its own partition table without touching Espressif files.

### 3.4 Critical finding — `{runtime.platform.path}` breaks under a core reference

The Boards Manager release of the core (generated by `build-packages.sh`) rewrites toolchain paths to `{runtime.tools.*}`, **but these remain on `{runtime.platform.path}`**:

- `tools/partitions/{build.partitions}.csv` (partition selection)
- `tools/partitions/boot_app0.bin` (merge, upload, export)
- `tools/gen_esp32part.py` (partition binary)
- `tools/flasher.py` (upload prefix)
- `tools/espota.py`, `tools/gen_insights_package.py`
- OpenOCD and SVD debug paths

Per the spec, `{runtime.platform.path}` is the **board** platform folder (VTLabs), so a naive VTLabs package would compile the sketch but fail at partition generation and upload.

**Fix (documented, Arduino CLI ≥ 1.0.4):** add to the VTLabs `platform.txt`:

```
runtime.use_core_platform_path_for_runtime_platform_path=true
```

This makes `{runtime.platform.path}` resolve to the referenced core platform.

**Unresolved:** (a) the spec documents the property's effect but not explicitly which file must set it — Stage 2 must confirm by compiling with it in VTLabs `platform.txt`, and by confirming the failure without it; (b) the minimum Arduino IDE 2.x release that bundles Arduino CLI ≥ 1.0.4 is not yet verified — check the IDE release notes. Arduino IDE 1.8.x is out of scope.

## 4. Architectural decisions this implies

1. **Platform layout:** VTLabs package vendor `vtlabs`, architecture `esp32`, FQBN `vtlabs:esp32:<board_id>`. Proposed board id: `vtlabs_iot_esp32_r1` (hardware revision in the id so future revisions get new ids rather than silently changed pins).
2. **No copy of the Espressif core.** VTLabs ships `boards.txt`, a small `platform.txt` (name, version, the runtime-path override), `variants/vtlabs_iot_esp32_r1/`, and VTLabs libraries.
3. **Core-version guard:** because the index cannot pin `esp32:esp32`, add a prebuild hook or a compile-time `#error` check in the VTLabs variant that fails clearly when the installed core is outside the supported range. Mechanism to be validated in Stage 2 (the core exposes `ESP_ARDUINO_VERSION_*` macros — verify in `cores/esp32/esp_arduino_version.h` before relying on them).
4. **Menus:** only expose menus that are valid for the actual module (e.g. drop PSRAM if absent, fix flash size to the real chip).

## 5. Blocking unknowns — hardware identification

Nothing below can be inferred; it must come from the physical board and schematic.

| # | Question | Why it matters |
|---|---|---|
| H1 | Exact module marking (e.g. ESP32-WROOM-32E, -32UE, -32D, ESP32-WROVER-E, ESP32-S3-WROOM-1…) | Selects chip family, `build.mcu`, toolchain |
| H2 | Flash size, and PSRAM present or not | Flash menu, partitions, PSRAM menu |
| H3 | USB path: dev-board USB-UART chip (CP2102 / CH340 / CH9102) or native USB | Upload method, driver guide, VID/PID detection |
| H4 | Is the dev module socketed on the trainer, or the bare module soldered? | Auto-reset circuit and boot pin behaviour |
| H5 | Schematic / netlist: every GPIO → peripheral (LEDs, buttons, switches, pot, LDR, buzzer, relay, display, sensors, headers) | Variant pin map |
| H6 | Which peripherals are physically fitted (display type + controller, I²C sensors + addresses, RS485 transceiver, SPI device) | Which curriculum examples are allowed |
| H7 | Board revision label (e.g. "Rev A") | Board id and versioning |
| H8 | Target IDE: Arduino IDE 2.x only, or must 1.8.x also work? | Runtime-path fix needs CLI ≥ 1.0.4 |

Quick self-check for H1–H2 on a real board: with the Espressif core installed, run `esptool chip-id` and `esptool flash-id` against the board's port; the output reports chip revision, features (e.g. "Embedded PSRAM") and detected flash size. (Command names follow esptool v5 hyphen style used by core 3.3.x — confirm with `esptool --help`.)
